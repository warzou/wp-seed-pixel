## Ownership decision

Retain M2 persistent item/job leases, immutable generations, revision CAS and
reconciliation. Replace Files::lock authority with a nonblocking MySQL/MariaDB
connection-owned advisory lock, scoped by database, site table prefix and
attachment (0 is the existing site coordinator). No new parallel lock table.
The existing job/item owner tokens still fence every durable stage transition.

A lease row alone cannot prevent a paused old worker from resuming an IO effect
after expiry. The session lock therefore MUST NOT expire with the M2 lease.
A live connection blocks takeover even after expiry. Process death closes the
connection; only then can an expired lease be reconciled by the next worker.
Owner-checked release, connection identity and IS_USED_LOCK checks reject lost
sessions/reconnections and stale local handles. DB unavailable means no effects.
Flock is not consulted on supported DBs, including the lying-flock test.
Claims use timeout zero: contention never waits or inverts lock order. The
coordinator takes site 0 then attachment, and all handles are released in finally.
Lease renewal at stage boundaries checks the live session, item token and CAS
revision. A slow encode cannot confer ownership on a second live worker.

Supported deployment topology is one primary MySQL/MariaDB server and stable,
nonpersistent per-request WordPress connections. Multi-primary routing, read
replicas used for lock queries, persistent pools and SQLite are not certified.
The advisory name includes database and site prefix; its maximum length is 64.
Both MariaDB and MySQL are now tested as executable engines in the disposable
lab; the initial checkpoint had only MariaDB runtime evidence. The final gate
above separately records the real Percona-backed NFS authority observation.
Sources: [MySQL locking functions](https://dev.mysql.com/doc/refman/8.4/en/locking-functions.html),
[MariaDB GET_LOCK](https://mariadb.com/docs/server/reference/sql-functions/secondary-functions/miscellaneous-functions/get_lock).

MySQL/MariaDB multiple named-lock semantics and actual contention/death tests
are required. SQLite is not an ownership backend; unsupported DBs fail closed
for processing. Historical SQLite tests remain historical evidence. No DB lock fences unrelated editors or an
arbitrarily suspended worker across database-server failure and remote filesystem
effects: those boundaries still need fresh checks/reconciliation and host gates.
Do not claim a portable atomic transaction spanning SQL and media files.

## Capacity decision

A separate small per-site settings option stores byte-valued informational
provider quota, operational ceiling, uncertainty reserve, safety reserve and
measurement freshness. Ceiling defaults disabled. Trusted accounting adapter
must supply complete upper-bound current usage, including local recovery;
unknown/incomplete/stale readings block configured-ceiling work.
The trusted adapter must explicitly declare `live=true` and recompute on every
invocation, including within the same second. An unexpired cached total is not
accepted. M1 media-only totals are evidence, not an entire hosting-account total.

One site coordinator is held through each allocation/effect. This serializes
Pixel admission; persistent candidates/recovery MUST be present in the next
adapter reading. Physical free-space and existing per-operation capacity guards
remain independent. Never borrow provider reserve or finance peak with savings.
No automated permanent purge. External growth not covered by the adapter remains
an explicit accounting limitation, not a fabricated whole-host guarantee.

## Future uploads decision

Explicit OFF / analyze / process opt-in, a durable generation plus maximum
attachment ID at enablement, and provenance on newly inserted attachments.
Only a completed create-metadata path for a proven new generation queues a
bounded persistent enrollment. Update/regeneration of old metadata is excluded.
Enrollment creates the existing M2/M3 job, not another image executor. A cron
adapter resumes that coordinator; failures never invalidate the WordPress upload.
An upload may already exceed the ceiling before this hook; Pixel blocks its
additional peak rather than claiming it prevented those incoming bytes.

Default M3/M4 execution stays disabled outside the disposable local test gate.
An explicit `WP_SEED_PIXEL_STORAGE_ENABLED=true` permits future host certification,
but never replaces private-root/same-device/ownership/metadata/IO preconditions.
No consumer enabling/deployment, PNG
M6, version bump, artifact rebuild, push or release is part of this milestone.
