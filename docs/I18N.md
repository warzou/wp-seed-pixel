# Internationalization

Text domain: `wp-seed-pixel`. English source strings remain generic. Bundled
French catalogue: `languages/wp-seed-pixel-fr_FR.po` and its standard GNU MO.
WordPress resolves the user locale; no hardcoded locale switch or gettext filter.
Loading is registered on `init`, before normal administrator UI rendering.

Run `python tools/i18n.py` after editing `tools/i18n-fr.json` or source strings.
This deterministic compiler validates missing translations and printf parameters,
creates the POT/PO/MO files, and checks the MO with GNUTranslations. The authoring
dictionary is tooling only; it is not shipped in the installable plugin ZIP.

Engine errors and stored decision reasons stay byte-identical English technical
evidence. `WP_Seed_Pixel_I18n::message()` translates known literals at the escaped
administrator presentation boundary only. Unknown external/raw diagnostics are
preserved rather than falsely translated. The generated literal inventory remains
extractable with normal WordPress gettext tooling. No HTTP payload paths exposed.

JavaScript receives translated strings through existing `wp_localize_script`.
Counter variants are resolved with `_n` for 0, 1 and 2 in PHP; JavaScript selects
the appropriate count category. This preserves French zero/singular behavior
without replacing the processing state machine or adding a JS dependency.

The processing signature keeps engine version `0.3.1`; the plugin/UI release
is `0.3.2`. The config hash substitutes this constant with the exact previous
value, so a language-only update does not invalidate existing generations.
No algorithm, thresholds, backend or output policy changes.

QA must distinguish catalogue/unit contracts, isolated rendered preview,
real WordPress en_US/fr_FR tests and consumer DEV checks. None authorizes a
processing job on real media or changes automatic-upload settings.
